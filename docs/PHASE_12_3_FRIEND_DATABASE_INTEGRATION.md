## Export inspection and restore

`Dump20261116.sql` was generated by MySQL 8.0.46. It contains 107 InnoDB tables with primary keys, 312 named secondary indexes, 219 foreign keys and 1,092 inserted rows across 58 tables. The migration ledger contains 293 distinct names in 86 batches. Only 172 names match the 182 regular integration migrations. Ten integration migration names were absent and 121 names appeared only in the dump. The dump also differs from the original local database by both table and migration names. Its SHA-256 is `769124a273dce4b4c922b8bea0c59b366eb9a7609d7a036f39aca1f128e9e380`.

The export includes account and password-hash data, addresses, session or cache payloads, messages, order history, and financial and custody records. Keep the dump and its restored data private. The report contains only metadata and aggregate counts.

The static scan found 107 `DROP TABLE IF EXISTS` statements scoped to the 107 unqualified table definitions. The parser accepted the expected MySQL session settings, locking and key toggles, DDL and literal row inserts. It found no database selection or creation, database-qualified objects, routines, triggers, scheduled events, file-loading statements, or client redirection. The unmodified file was restored only after confirming the checksum and an empty target.

The restore ran on MySQL **8.0.44**, `127.0.0.1:33183`, in `zefanya_friend_test`. The instance uses its own data directory and has no `zefanya` schema. The import account had grants only on the exact restored schema, and MySQL returned access denied for `USE zefanya`. Local file loading and automatic reconnect were disabled. Post-restore checks matched all 107 table row counts against the dump. Referential checks found three existing audit rows whose Admin is missing from `platform_setting_histories`. These remain untouched. The metadata and migration ledger of the original local `zefanya` on port 3306 matched byte-for-byte before and after the work. The original database received only read-only inspection.

## Compatibility findings

The initial comparison found four integration tables absent from the dump and eight dump-only tables. Across the shared tables, five integration columns were missing, 14 extra columns were present and 23 common column definitions differed. There were 12 missing FK shapes and two additional FK shapes when compared by columns, referenced table and update/delete behavior. Some index differences were naming differences. The complete metadata comparison, including index column order and foreign-key behavior, is in `import-schema-diff.json` in the isolated rehearsal directory. It contains no business records.

| Area | Finding and handling |
|---|---|
| Checkout recovery | The dump has `shipping_rates_snapshot` and all 10 original token snapshots. It lacked `order_id` and `reconciled_rejected_at`. The integration API requires both. The existing migration added them with a nullable FK to orders. Six used legacy tokens have no proven link to an order and remain unknown to reconciliation. |
| Proof and COD | The dump had four proofs and four COD remittances. Nullable recipient acknowledgement was added. No past recipient or acknowledgement was inferred. The two existing COD shortage columns gained their Rider and provider deletion restrictions after reference checks. |
| Transfer Courier | Assignments and the Courier account table exist. The dump contained zero Courier accounts. The manifest assignment FK originally cascaded deletes. The compatibility migration verified the three existing manifest references, installed the restriction, then removed the cascade. It also added the missing assignment actor FKs on manifests and handoffs. Courier accounts were created only on the independent synthetic schema. |
| Shipping and paid cancellation | Applied the existing migrations for empty `shipping_rates` and `payment_cancellation_refunds` tables. The imported provider rates and historical price snapshots were preserved. No historical rate or refund liability was inferred. |
| Promos and vouchers | The dump ledger records an intentional drop of the two Seller promotion tables. They remain absent. Platform-voucher structures remain intact. Historical promotions and rate-card contents require a decision or a separate authoritative export. |
| Loss, payouts, returns and refunds | The import uses different parcel-loss actor and date fields. Its narrower columns and missing FKs include loss and operational audit fields. The imported schema already has the refund policy version field, with no populated version on its four returns. The rehearsal did not alter that activation state. Seller payout, settlement and platform-funded voucher tables exist, with no payout or voucher history imported in those tables. |

Four explicitly selected migrations ran on the restore. The other mismatched migration files require a reviewed cross-history plan before execution. No migration was manually marked applied. The post-change schema has 109 tables, 297 migration records and 227 FKs. The original columns of all 106 non-ledger tables had identical row counts and SHA-256 row digests in primary-key order. Repeating the selected migration command returned “Nothing to migrate.” The friend-import bridge refused a wrong schema and refused disabled foreign-key checks. It validates references before DDL and sits outside Laravel’s normal migration path.

### Start the local synthetic rehearsal

These commands use the current machine's isolated files under `%LOCALAPPDATA%\Temp\zefanya-phase123-friend`. Each terminal starts a foreground process. Leave a running process alone if its port is already open and belongs to the rehearsal.

1. If the separate MySQL instance is stopped, start its existing data directory in PowerShell. It is already initialized.

   ```powershell
   $phase = Join-Path $env:LOCALAPPDATA 'Temp\zefanya-phase123-friend'
   & 'C:\Program Files\MySQL\MySQL Server 8.0\bin\mysqld.exe' --no-defaults "--datadir=$phase\mysql-data" --port=33183 --bind-address=127.0.0.1 --mysqlx=0 --local-infile=0 --event-scheduler=OFF --skip-log-bin "--pid-file=$phase\mysql.pid" "--log-error=$phase\mysql.log"
   ```

2. Start Laravel in a second terminal. The launcher verifies the separate MySQL process, schema and data directory before opening the server. Open `http://127.0.0.1:38129` for Web.

   ```powershell
   $phase = Join-Path $env:LOCALAPPDATA 'Temp\zefanya-phase123-friend'
   & "$phase\start-synthetic.ps1"
   ```

3. Start the local HTTPS API proxy in another terminal. The protected API client requires HTTPS. For Chrome, trust the specific local certificate through your normal development certificate workflow. The generated certificate covers `127.0.0.1` and has a short expiry.

   ```powershell
   $phase = Join-Path $env:LOCALAPPDATA 'Temp\zefanya-phase123-friend'
   python "$phase\tls-proxy.py" $phase
   ```

4. Run Flutter from the project's `mobile` directory. For an Android emulator, the host address is `10.0.2.2`. Use a trusted certificate covering that address before changing the URL from the Chrome command.

   ```powershell
   flutter run -d chrome --dart-define=USE_LIVE_API=true --dart-define=zefanya.backend=webzefanya --dart-define=zefanya.webzefanya.apiBaseUrl=https://127.0.0.1:38130/api --dart-define=zefanya.webzefanya.courierApp=true --dart-define=zefanya.webzefanya.allowWrites=false --dart-define=zefanya.webzefanya.allowVerifiedWrites=true --dart-define=zefanya.devTools=false
   ```

The generated synthetic sign-in details are stored locally in `http-fixture.json` in the rehearsal directory. The Web launcher uses the verified Laravel copy recorded in `web-path.txt`.
