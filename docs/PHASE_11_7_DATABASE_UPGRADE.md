# Phase 11.7 database compatibility and upgrade requirements

See the [Phase 12 stabilization report](PHASE_12_MYSQL_STABILIZATION_REPORT.md) for the corrected barangay rollback and the read-only comparison against the actual populated database. The findings below record the earlier rehearsal.

The integration baseline is `20c9bb1` on `integration/phase11-stable`. The `webzefanya-live` reference was the supplied `migrations.zip`, SHA-256 `2a89931d5ce6e70a9753345f6bbf218eae6495d5e2c06fe15732bb65c0d05142`. The archive was extracted to a temporary directory. Each migration history was applied independently to an empty schema on a separate, loopback-only MySQL 8.0.44 instance on port `33179`. Before each write, the test runtime checked the resolved database name, port, and MySQL data directory. The populated `zefanya` database was left untouched.

## Migration history and schema comparison

| Schema | Migrations applied | Tables including the ledger | Indexes | Foreign keys |
|---|---:|---:|---:|---:|
| `webzefanya-live` reference | 103 | 106 | 414 | 218 |
| Integration baseline | 182 | 103 | 408 | 224 |
| Integration plus explicitly pending Courier account migration | 183 | 104 | 411 | 225 |

Four files match by relative path and normalized content: the three Laravel framework migrations and `2026_11_15_000000_drop_delivery_otps_table.php`. The remaining 99 reference files and 180 integration files (including two pending files) have distinct names. Neither migration set duplicated literal `Schema::create()` targets in its regular files or hit a foreign-key order failure on a fresh database. Combining the histories would mix different create migrations for the same tables, including `buyers`, `reviews`, and `personal_access_tokens`. The reference's `verify_old_migration_history` guard accepts zero or all 183 named legacy entries. It would reject the integration ledger, which matched 168 of the 183 names even after a successful fresh build.

## Fresh MySQL and Web–Mobile rehearsal

The working checkout had no `web/.env` or cached Laravel configuration. The isolated Laravel copy matched all 4,386 tracked Web files before test-only corrections. The normal migration command completed on both empty schemas, and the pending Courier account migration completed separately on the integration demo schema. The server's crash-durability settings were relaxed only on the disposable MySQL instance to speed up the remaining synthetic test writes. Crash or failover behavior was outside this rehearsal.

`SpecShippingRateSeeder`, `AdminSeeder`, and the guarded `DemoMarketplaceSeeder` completed on the integration demo schema. Run `AdminSeeder` before the demo marketplace with a fresh local-only Admin identity. Without it, `DeliveryScenarioSeeder` cannot set up partnerships and the first coverage seeder reports a missing provider. The demo guard was used with the exact disposable schema name. The demo scenarios verified direct, intraprovince, interprovince, inter-island, and unsupported destinations. No seeders from the ZIP were available because the archive contains only migrations and their documentation.

These checks used raw HTTP against loopback Laravel and a separate Flutter repository test against those same records over trusted loopback HTTPS. A browser, physical device and production backend were outside the rehearsal. The WebZefanya release write allowlist was left in place. In particular, the HTTP return test does not authorize the Flutter release to submit returns.

Test cases were adapted for native MySQL. The return audit and product dimensions tests compare the exact JSON keys, types and values independent of object key order. The legacy address test compares the stored snapshot before and after verification. SQL failure injection uses the connection's identifier quoting so the original rollback and file-cleanup assertions also execute on MySQL. The station coverage fixture uses a synthetic code of the correct length. The database comparison resulted in test-only changes. Phase 11.9 separately fixed the shared Seller status display.

The historical barangay migration's `down()` guard emits a grouped `SELECT *` under `EXISTS`. MySQL 8 with `ONLY_FULL_GROUP_BY` rejects it with error 1055 before it can evaluate whether municipalities have multiple barangay claims. Both forward histories passed. The existing migration file was preserved as requested. Use snapshot restoration as the recovery plan, and resolve or formally retire the reverse migration before a populated upgrade. A future approved correction can select a constant or grouped key in that guard while keeping the refusal to merge multiple coverage records.

The 129 focused native integration cases passed. Across the complete 4,298-case Laravel suite and focused retests, the latest measured native outcomes were 4,283 passed, 2 failed, 8 errors and 5 skips. See [the integration report](FINAL_WEB_MOBILE_INTEGRATION_REPORT.md) for the remaining test-harness and schema findings. The fresh-schema result is PASS. The populated upgrade remains BLOCKED pending an exact backup rehearsal and recovery plan.

## Safe upgrade of the populated database

1. Obtain a verified backup of the intended database and restore it to a dedicated disposable instance. Capture the migration ledger, exact definitions, constraints, indexes and row counts. Earlier local evidence recorded 47 matching Phase 11.5 migrations, 133 then-unrecorded migrations, and 17 older entries. Those are historical counts and need refreshed evidence from the copy.
2. Choose one forward migration history. Classify existing tables as equivalent, missing, or incompatible. Reconcile `reviews`, `personal_access_tokens`, `shipping_rates`, and role archive fields by actual definitions. Do not insert migration ledger rows based on table names or copy the reference directory over integration.
3. Add fields and indexes before any backfill. Preserve Buyer ownership, historical checkout snapshots, recipient evidence and custody history. Backfill only from verifiable records. Check orphaned foreign keys, duplicate keys and values that would exceed narrower reference types before adding constraints.
4. Reconcile voucher funding, inventory, COD, refunds, loss compensation, Seller debts and payouts before and after the upgrade. Review Courier activation and the pending refund policy independently. Require a rollback rehearsal and backup restoration test before authorizing any populated-database change.
