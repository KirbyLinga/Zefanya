# Zefanya — Project Overview

## What the application is
A multi-vendor e-commerce marketplace (Shopee/Lazada-style workflows, original UI/code) built as a **monolithic Laravel app**: Laravel + PHP 8.5, MySQL, Eloquent, Blade, Tailwind CSS v4 via Vite, Laravel Breeze-style auth, PHP backed enums for statuses. Icons: lucide (`<i data-lucide>`) + Font Awesome. Fonts: Playfair Display (`font-serif`), Montserrat (`font-sans`).

## Five roles
1. **Buyer** — browse, cart, checkout, pay, track, profile/addresses.
2. **Seller** — store, products, inventory, receives orders, fulfils up to READY FOR PICKUP.
3. **Logistics** — owns the ENTIRE courier lifecycle: courier applications, approval, courier records, assignment, delivery monitoring.
4. **Courier** — handles only deliveries assigned to them.
5. **Admin** — marketplace administration; does NOT own courier management.

## Order architecture (settled — do not restructure without approval)
```
orders → seller_orders → order_items
seller_orders 1—1 payments
seller_orders ← inventory_transactions (append-only stock ledger)
courier_applications → (Logistics approval) → couriers
```
- `orders.buyer_id → buyers` (RESTRICT); `seller_orders` unique `(order_id, seller_id)` — one slice per shop per order; `payments` unique `seller_order_id` (1:1, per seller_order, NOT per order).
- `orders`, `seller_orders`, `order_items`, `payments`, `inventory_transactions` are permanent records: never soft/hard deleted; cancel via status instead. FKs are RESTRICT (except `order_items.product_id` SET NULL).
- Money is unsigned-integer **centavos** everywhere, columns suffixed `*_minor` (subtotal/discount/total on `orders`, subtotal on `seller_orders`, amount on `payments`, price on `order_items`).
- `orders.shipping_address` is a JSON **snapshot** of the buyer's profile address at order time, not a live FK.
- Voucher discounts are allocated proportionally across seller_orders (largest-remainder) so per-shop COD payments sum exactly to `orders.total_minor`.
- No `deliveries`/`shipments`/courier tables yet — delivery pipeline is Phase 3.

## Database / status conventions
- Status columns are **VARCHAR**, never MySQL ENUM; values handled by **PHP backed enums** cast in models (`App\Enums\OrderStatus` = PLACED…RETURNED pipeline; `App\Enums\PaymentStatus` = pending|paid).
- Money columns are unsigned integer centavos suffixed `*_minor`; never floats or decimals for order money.
- Migration naming follows `2026_MM_DD_HHMMSS_snake_case_name.php`; never edit an executed migration — create a new one.
- Buyer-facing tables use the **buyer guard** (`App\Models\Buyer\Buyer`, provider `buyers` in `config/auth.php`). There is no `users`-table buyer.

## Checkout + orders (current phase — DONE, verified 2026-10-05)
- **Schema** (migrations `2026_09_22_110001…110005`, NOT yet run by the agent — developer runs `php artisan migrate` on the live DB): `orders`, `seller_orders`, `order_items`, `payments`, `inventory_transactions` per the settled architecture above. `reference` = `ORD-YYYYMMDD-XXXXXX` unique.
- **Models**: `Order` (buyer→Buyer, hasMany sellerOrders; casts: status enum, address array, *_minor int; `Order::generateUniqueReference()` + `rollUpStatus()` / `computeRollupStatus()` / `canBeConfirmed()`; `status` NOT mass-assignable — written via `forceFill`); `SellerOrder` (order + seller + hasMany items + hasOne payment); `OrderItem` (product_name/price snapshots, `lineTotalMinor()`); `Payment` (PaymentMethod/PaymentStatus casts, `markPaid()`; `status` NOT mass-assignable); `InventoryTransaction` (append-only ledger). `App\Exceptions\CheckoutException` for in-transaction aborts.
- **`CheckoutController@store`** (`buyer.checkout.store`, live 500 fixed): reads parked `checkout_item_ids` + `cart_voucher`; re-resolves from the LIVE cart scoped to the buyer (tampered/missing ids → flash error + redirect to cart, never silently drop); re-validates availability + stock; `Voucher::resolveCode` re-validation identical to index (invalid voucher → dropped with notice, order still places); totals only from `CartSummary`; then one `DB::transaction()` (product rows `lockForUpdate()` ordered by id, stock re-checked under lock, order + one SellerOrder per shop + OrderItems + one pending COD Payment per shop + stock decrement + `inventory_transactions` rows reason `checkout`); sets `orders.status` to `Placed` via `forceFill`; success deletes ONLY the selected cart lines, forgets both session keys, redirects to `buyer.checkout.success` (ownership 404 for other buyers).
- **Parent order status rollup** (`Order::rollUpStatus()` / `computeRollupStatus()`): when any `seller_orders` row transitions, `SellerOrderStatusService` re-queries all sibling seller_orders under the parent's row lock and re-derives `orders.status` = bottleneck (min pipeline rank among non-Completed slices) or `Completed` when all slices are Completed. `status` is written via `forceFill` (NOT in `$fillable`), matching the CheckoutController pattern.
- **COD payment settlement** (`Payment::markPaid()`): called from `SellerOrderStatusService` when a seller_order reaches `Delivered` (cash collected at door) or `Completed` (buyer confirmed, safety-net). Guards on `method === Cod` + `status === Pending`; null-safe on missing payment row; idempotent (re-calling on an already-paid payment is a no-op since `markPaid()` checks `paid_at`). Settlement runs INSIDE the transition's `DB::transaction` alongside the parent rollup — a throw rolls back the seller_order status change too.
- **Confirm received** (`Buyer\OrderController@confirmReceived`): 404 if order doesn't belong to buyer; gated by `Order::canBeConfirmed()` (true only when every seller_order is Delivered-or-Completed AND at least one is still Delivered); wraps all slice transitions in `DB::transaction` (the service's inner transaction becomes a savepoint). Flash `error` if not confirmable ("There are no delivered items to confirm right now."); flash `success` on success.
- **Resync command** (`orders:resync`): chunks orders eager-loading `sellerOrders.payment`, re-derives parent rollup status, settles COD for Delivered/Completed slices; `--dry-run` is a no-op (no writes).
- **Confirmation page**: `Buyer/Checkout/success.blade.php` — reference, status, per-seller groups with COD amounts, order totals, address snapshot, links to orders/home. No new Vite inputs.

## Security rules (non-negotiable)
- `$fillable` allow-lists only (never `$guarded = []`); `status`/`courier_id` never mass-assignable from requests.
- Sensitive models get Policies; never rely on controller checks alone.
- Stock ops: `DB::transaction()` + `lockForUpdate()` + `inventory_transactions` row; never bare `decrement()`.
- Buyer sees only own cart/orders; seller only own seller orders; courier only own deliveries.
- Applied vouchers/discounts are always re-validated server-side; client-sent amounts are never trusted.

## Mail / OTP (verified 2026-09-26)
- **Transport**: Gmail SMTP (`MAIL_MAILER=smtp`, `smtp.gmail.com:587`, app-password auth in `.env`). `MAIL_SCHEME` is deliberately unset — Laravel 12 reads `MAIL_SCHEME`, **not** `MAIL_ENCRYPTION` (the `MAIL_ENCRYPTION=tls` line in `.env` is inert); the `smtp://` DSN on port 587 still upgrades to STARTTLS.
- **`APP_NAME` in `.env` MUST stay `Zefanya`.** It drives `config('mail.from.name')` (via `MAIL_FROM_NAME="${APP_NAME}"`) **and** the header/signature/footer of every notification mail. With the scaffold value `Laravel` the OTP mail went out as `Laravel <penguinskipper9@gmail.com>` while the subject said "Your Zefanya verification code" — brand mismatch + code body = phishing pattern → Gmail spam (developer report: "the OTP is not sending").
- **OTP notifications are NOT queued** (`BuyerVerifyOtp`, `SellerRegistrationOtp`, `LogisticsRegistrationOtp` have no `ShouldQueue`), so `QUEUE_CONNECTION=database` plus no `queue:work` cannot delay them — they send inline and throw on transport failure. All three notifiables (`Buyer`, `Seller`, `LogisticsProvider`) use `Notifiable` + `fullName()`; `BuyerVerifyOtp::toMail()` needs `$notifiable->fullName()`, so it cannot be sent to an `AnonymousNotifiable` (use a real model or `Notification::route` with a custom message).
- **Codes**: 6 digits, 10-minute expiry, `sha256` hash stored on the model, `issueOtp()` returns the RAW code for the mail; throttles: store 5/min, verify 10/min, resend 3/min (buyer resend 3/min, seller/logistics resend 3/5 min).
- **Diagnosing "OTP not sent"**: `storage/logs/laravel.log` gets `WARNING: … OTP sent` only AFTER a successful `notify()`, so a missing line means the send threw (the request 500s / the modal shows "Registration failed"). To inspect what the recipient sees without sending: `(new BuyerVerifyOtp('123456'))->toMail($buyer)->render()`.

## What was implemented 2026-10-05 (parent rollup + COD settlement + confirm gate)
- **`Order::computeRollupStatus()` / `rollUpStatus()`**: pure computation + persistence of parent `orders.status` from its `seller_orders` collection. Bottleneck = min pipeline rank among non-Completed slices; short-circuit to `Completed` only when ALL slices are Completed. `status` written via `forceFill` (NOT in `$fillable`).
- **`Order::canBeConfirmed()`**: true only when every `seller_order` is Delivered-or-Completed AND at least one is still Delivered (i.e. there's an unconfirmed slice and none left in transit).
- **`Payment::markPaid()`**: `forceFill` sets `status = Paid` + `paid_at = now()`. Idempotent (checks `paid_at` before setting).
- **`SellerOrderStatusService::transition()`**: calls `rollUpParentOrder()` + `settleCodPayment()` INSIDE the existing `DB::transaction`. COD settlement triggers on both `Delivered` and `Completed` transitions; guarded on `method === Cod` + `status === Pending`; null-safe on missing payment row.
- **`Buyer\OrderController@confirmReceived()`**: 404 if order doesn't belong to buyer; `canBeConfirmed()` gate (flash `error` if not); wraps Delivered→Completed transitions in `DB::transaction`; flash `success` on success.
- **`OrdersResyncCommand`** (`orders:resync --dry-run`): chunks orders eager-loading `sellerOrders.payment`, re-derives parent rollup, settles COD for Delivered/Completed slices.
- **`PaymentFactory`**: created with `seller_order_id`, `amount_minor=10000`, `method=Cod`, `status=Pending`, `paid_at=null`, and a `paid()` state.
- **View**: `Buyer/Orders/show.blade.php` updated with confirm-received button + delivery messaging; fixed dead `@elseif` branch.
